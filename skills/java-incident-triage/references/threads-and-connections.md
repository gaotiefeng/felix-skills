# 线程、线程池与连接池：证据判断

## 连接池耗尽

`active=max`、`idle=0`、等待线程增加可以支持当前池容量耗尽，不能直接证明泄漏，也不能推出数据库全局连接达到上限。对照应用等待、连接持有栈、事务年龄、执行中 SQL 与数据库阻塞链，尽量使用同一时间窗口。

数据库 Sleep 会话可能是正常池内空闲连接；即使存在 Sleep 中的未结束事务，也应确认事务归属与持有路径。锁等待查询为空只说明采样时未捕获，不能排除此前阻塞。

如果栈显示持有连接后等待 HTTP，下游超时与事务范围应成为检查重点；若大量线程只在 getConnection 排队，这些往往是受影响者，还需找持有者。

扩大连接池可能把压力转给数据库。建议前核对数据库连接预算、同机/多实例总池容量、查询耗时和吞吐，不把单个历史事故的数值作为默认配置。

## 线程池

标准 ThreadPoolExecutor 的有界队列行为：先达到核心线程，再入队，队列无法接收时才增加线程到最大值，之后拒绝。分析拒绝前先看是否 shutdown，不把所有拒绝都解释成容量不足。

CallerRunsPolicy 会在提交线程上执行任务；shutdown 后任务会被丢弃。它可形成反压，但不提供持久化、重试或必达。分析请求线程提交慢任务时，要考虑接口延迟；若只看到配置，不能断言事故中已触发该策略。

线程名后缀是命名序号，不是实时存活线程数。确认实际执行器要结合 Bean 选择、显式 @Async 名称、框架版本、线程栈与配置；仅看到多个执行器不能断言一定回退到某实现。

## 线程等待与 CPU

线程池空闲线程在队列等待通常正常；RUNNABLE 也可能处于原生 I/O。BLOCKED 数量或一份线程栈不能独立证明死锁。检查锁的持有者、等待关系或 JVM 死锁报告；跨资源死锁可能需要数据库证据。

持续问题可建议间隔采样少量线程栈，明确实例和时间；不保证固定三份一定定位。高 CPU 需要线程级 CPU 与同时间线程栈关联，只有日志时应提出缺少的采样，而不是猜 GC 或死循环。
