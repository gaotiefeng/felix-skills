# 并发与资源：查所有权和失败路径

## 并发

从真实共享对象与线程入口开始。局部变量不是自动线程安全的保证，它也可能引用共享对象；单例 Bean 的可变字段需要结合写入与访问路径判断。

对“检查后更新”“先查后插”给出具体交错，检查数据库唯一约束、原子操作、锁、版本条件及失败处理是否已经兜底。不能因为使用 ConcurrentHashMap 就认为任意复合操作都原子，也不能无视数据库约束而直接报告重复数据。

锁需要覆盖同一共享资源、在正确的 finally 路径释放；对于中断，检查是否继续传播、恢复标记或按明确协议退出，不能机械要求每个 catch 都重复设置中断。

## 执行器

有界线程池先达到核心数，再排队，队列满才向最大线程数扩展。无界队列可能造成积压；是否为缺陷应结合提交速率、任务寿命和负载约束。

CallerRunsPolicy 可能让提交线程同步执行，shutdown 后丢弃；它不是可靠投递。请求线程、持锁线程或事件循环提交时，核对同步执行造成的影响。不要在无触发条件时把策略本身当作 bug。

同一池内的任务提交子任务并阻塞等待，可能形成线程饥饿；应展示所有工作线程被父任务占用且子任务排队的可达场景。

submit 返回 Future 的异常需要被观察，但无人读取 Future 是否为问题取决于任务内部错误处理与业务要求。

## 资源所有权

对连接、ResultSet、文件流、HTTP 响应体和锁，沿创建、转移、正常退出、异常退出检查关闭责任。优先用 try-with-resources 处理明确归当前方法所有的 AutoCloseable。

框架托管、借用或交给调用方的资源不能一概由当前方法关闭。例如共享执行器通常由容器生命周期管理，不能要求每次请求 shutdown；Spring 管理事务连接要遵循其获取/释放约定。

评审读取大文件或导出时，检查是否一次性累积结果、是否有数据量上限、异常时是否释放资源。没有业务上限信息时，给出条件化风险而不是声称必然 OOM。
