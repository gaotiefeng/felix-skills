# 索引与执行计划

## 索引设计

先对照已有定义，包括唯一性、列顺序、前缀长度、表达式、可见性和排序方向。相同列集合不意味着索引等价；疑似冗余索引也可能承担唯一性或外键需求，未核对工作负载不能直接删除。

联合 B-tree 索引通常依赖最左前缀形成高效查找，但优化器也可能选择覆盖扫描或版本支持的 skip scan，不能说“不含首列必然完全不能使用索引”。等值、范围、排序的组合要看实际访问范围和计划，不能把“范围条件之后所有列都无用”作为规则：后续列可能参与过滤、覆盖等。

不要机械把区分度最高列放第一。还需考虑常见查询前缀、排序、范围、LIMIT和多租户访问。InnoDB 二级索引包含主键信息，覆盖判断要结合实际选择列与引擎，不要仅为返回主键重复添加同一列。

函数、隐式转换、字符集/排序规则不一致可能影响访问路径，但具体方向由类型和优化器决定；函数索引、生成列和不同版本能力也会改变结论。不能看到函数就一律断言索引失效。

## 阅读计划

传统 EXPLAIN 中 possible_keys 是候选、key 是所选，rows/filtered 是估算。key非空可能只是大范围索引扫描；type=ALL 在小表或需返回大部分数据时可以合理。Using filesort 不等于一定写磁盘，Using temporary 也不是独立的性能定罪证据。

JSON/TREE 格式要按节点读取驱动顺序、访问路径、过滤和排序，注意物化、相关子查询与连接放大。不把传统字段解释硬套到所有格式。

EXPLAIN ANALYZE 的实际行数、时间与 loops 要结合目标版本解释：重复执行节点通常显示每循环平均值，估算工作量可结合 rows×loops；父节点时间含子节点工作，不能直接把所有节点时间相加当总耗时。仪器开销、缓存状态和并发也可能影响实测。

估算与实际偏差较大时，检查参数偏斜、统计信息与谓词关联，再提出统计更新候选；ANALYZE TABLE 是会改变统计信息的操作，不自动执行。选择一个快参数不能证明所有租户和时间范围都快。

## 验证候选索引

在受控环境对比相同数据和参数下的结果、访问行数、循环数及端到端耗时。至少考虑常见参数、大结果集和偏斜参数。记录缓存与并发条件，观察写入和空间代价。DDL语法、在线能力与锁影响以实际版本为准；不默认加索引无锁、不默认支持回滚。
