# 查询语义检查

## JOIN 与聚合

确认一对一/一对多关系是否由唯一约束或业务保证。主表金额与多行明细 JOIN 后再 SUM 可能重复累计；COUNT(*)、COUNT(列) 和 COUNT(DISTINCT 主键) 含义不同。只需要判断明细是否存在时可考虑 EXISTS，但要确认原查询是否需要保留明细重复行。

LEFT JOIN 的右表条件放在 WHERE 可能排除 NULL 扩展行。是否有问题取决于是否需要保留无匹配主记录；移到 ON 会改变结果，不可不经判断机械移动。

## NULL 与集合

NOT IN 子查询可能产生 NULL 时，不能当作 NOT EXISTS 的等价替代；核对双方可空性及期望。UNION 与 UNION ALL 的重复行语义不同，去掉 DISTINCT 或去重操作必须有证据。

## 时间与分页

按天查 DATETIME 时，半开区间通常容易表达边界，但要核对字段类型、时区和参数类型。不要用结束时间23:59:59遗漏小数秒，也不要把业务时区切换当作单纯性能改写。

分页需要与业务匹配的稳定排序。时间相同时可用唯一键补充顺序。深 OFFSET 的改进可以考虑游标分页，但它会改变跳页能力，并需定义排序方向、相同时间的复合游标与并发更新行为，不能声称完全无行为变化。

LIMIT 不意味着只扫描对应行数。导出和聚合需看数据量约束；不能因为用了分页就假定 count 查询也便宜。

## 写入与权限条件

审查 UPDATE/DELETE 时首先确认目标集合和租户边界。即使索引提高速度，也不能修复缺少业务过滤的语义错误。不要为生成执行计划而擅自执行写语句。

## 示例

订单A金额100，有两条明细。按订单 JOIN 明细后 SUM(订单金额) 得到200。若需求为“有明细的订单总金额”，需要改变连接/预聚合方式；不能只推荐为 JOIN 字段加索引。
